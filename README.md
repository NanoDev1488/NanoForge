# NanoForge

Фреймворк-плагин для Bukkit/Spigot/Paper **1.16 – 1.21.11**, который позволяет
создавать **аддоны к другим плагинам** и **самостоятельные мини-плагины**
прямо на сервере — командами и YAML-описанием, без компиляции джарника.

Одна команда, одна YAML-схема, один движок исполнения — для команд,
событий и инвентарных меню одновременно.

## Возможности вкратце

- Создание аддонов к любому установленному плагину или самостоятельных
  мини-плагинов — командой, с табкомплитом по реально загруженным плагинам.
- Динамическая регистрация команд и событий Bukkit — ничего не нужно
  прописывать в `plugin.yml` заранее.
- Автоматический дамп классов/методов/полей целевого плагина (`target-api.txt`)
  — сразу видно, что можно вызывать через рефлексию.
- Вызов методов ЛЮБОГО плагина сервера (`type: call`) — без compile-time
  зависимости от него.
- Инвентарные GUI-меню произвольной вложенности, с редактором прямо в игре
  (перетаскивание предметов + чат-DSL для логики кнопок).
- Условия (`if`): права, мир, регион (WorldGuard), баланс (Vault), переменные,
  кулдауны.
- Плейсхолдеры (`{player}`, `{world}`, `{result}` и т.д.).
- Хранилище переменных/кулдаунов на аддон, без ручной настройки.
- Опциональные интеграции с Vault, WorldGuard, PlugMan/PlugManX — все через
  рефлексию, без обязательных зависимостей в сборке.
- Один битый `addon.yml` не роняет ни другие аддоны, ни сервер. Ошибки
  внутри логики не сыплют стектрейсами в консоль.

## Быстрый старт

```bash
mvn clean package
# получившийся target/NanoForge.jar — в plugins/ сервера
```

В игре (от админа, право `nano.admin`):

```
/nano create addon EssentialsX МойАддон
/nano enable МойАддон
/nano menu МойАддон main
```

Готово — сразу открывается рабочее меню-пример: кнопка с сообщением,
переход в подменю с примером вызова метода `EssentialsX`, кнопка закрытия.
Дальше редактируется через `/nano edit МойАддон main` или прямо в
`plugins/NanoForge/addons/МойАддон/addon.yml`.

## Команды

| Команда | Описание |
|---|---|
| `/nano create addon <плагин> <имя>` | создать аддон к существующему плагину (табкомплит на `<плагин>` — реальные плагины сервера) |
| `/nano create new <имя>` | создать самостоятельный мини-плагин |
| `/nano enable <имя>` | включить аддон |
| `/nano disable <имя>` | выключить аддон |
| `/nano list` | список всех аддонов и их статус |
| `/nano info <имя>` | тип, целевой плагин (и его статус), список команд/событий/меню, путь к папке |
| `/nano reload` | перечитать все аддоны с диска без рестарта сервера |
| `/nano menu <аддон> <меню>` | открыть GUI-меню |
| `/nano edit <аддон> <меню>` | открыть меню в режиме редактирования |

Алиасы: `/nanoforge`, `/nd`. Право на управление — `nano.admin` (по
умолчанию — только op). Команды, создаваемые внутри самих аддонов, по
умолчанию доступны всем игрокам (см. [Actions](#actions)).

## Структура хранения аддона

Каждый аддон — это **папка**, а не один файл:

```
plugins/NanoForge/addons/
  └── МойАддон/
      ├── addon.yml        - команды/события/меню/действия
      ├── storage.yml      - переменные и кулдауны (создаётся автоматически)
      └── target-api.txt   - дамп классов/методов целевого плагина
                             (только для type: addon, создаётся при создании аддона)
```

`target-api.txt` — при `/nano create addon`, если целевой плагин сейчас
активен, NanoForge рефлексией проходит по всем его классам и пишет для
каждого: родителя/интерфейсы, конструкторы, public/protected методы (с
типами параметров) и поля. Это шпаргалка для `type: call` — не нужно лезть
в декомпилятор, чтобы узнать, что вообще можно вызвать.

## Формат addon.yml

```yaml
name: МойАддон
type: addon           # addon - привязан к плагину, new - самостоятельный
target: EssentialsX   # только для type: addon
enabled: false

commands:
  vipshop:
    description: "Магазин для VIP"
    permission: nano.vip     # необязательно - право на саму команду целиком
    actions:
      - type: openmenu
        menu: main

events:
  PlayerJoinEvent:
    actions:
      - type: broadcast
        text: "&e{player} зашёл на сервер"

menus:
  main:
    title: "&8Меню"
    rows: 3
    items:
      "13":
        material: CHEST
        name: "&eОткрыть подменю"
        actions:
          - type: openmenu
            menu: sub
```

## Actions

Один и тот же список действий работает **везде**: в командах, событиях и
пунктах GUI-меню.

| type | параметры | что делает |
|---|---|---|
| `message` | `text` | сообщение отправителю/игроку |
| `broadcast` | `text` | рассылка всем на сервере |
| `console` | `command` | выполнить команду от имени консоли |
| `call` | `plugin`, `method`, `args`, `save_as?`, `scope?` | вызвать метод чужого плагина через рефлексию; результат доступен как `{result}`, опционально сохраняется в переменную (`save_as`) |
| `openmenu` | `menu`, `addon?` | открыть GUI-меню (своё или чужого аддона) — так строится любая вложенность |
| `closemenu` | — | закрыть текущее меню |
| `setvar` | `key`, `value`, `scope?` | сохранить переменную аддона (`scope: player` по умолчанию или `global`) |
| `addvar` | `key`, `amount`, `scope?` | прибавить число к переменной |
| `eco_give` / `eco_take` | `amount` | начислить/списать через Vault |

`call` находит инстанс плагина через `Bukkit.getPluginManager().getPlugin(name)`
и ищет метод с подходящим числом аргументов, приводя строки к
`String/int/double/boolean/long`. Полный список методов/классов — в
`target-api.txt` аддона.

События (`events:`) задаются коротким именем (`PlayerJoinEvent`,
`BlockBreakEvent` и т.д. — ищутся в основных пакетах `org.bukkit.event.*`)
либо полным путём класса для событий сторонних плагинов.

## Условия (if)

Необязательный блок `if:` внутри любого action или пункта меню. Если
условие не проходит — action пропускается (пункт меню — просто не
показывается).

| ключ | что проверяет |
|---|---|
| `permission` / `not_permission` | право есть / права нет |
| `world` | игрок в указанном мире |
| `region` | игрок физически в регионе WorldGuard с этим именем |
| `eco_at_least` | баланс Vault не меньше суммы |
| `var_equals` / `var_at_least` | переменная аддона равна / не меньше значения |
| `cooldown` | не чаще раза в N секунд на игрока (`seconds`, `key`) — при успехе сразу отмечает использование |
| `deny_message` | сообщение при провале (для `cooldown` доступен `{cooldown}` — оставшиеся секунды) |

```yaml
actions:
  - type: console
    command: "heal {player}"
    if:
      cooldown: { seconds: 30, key: heal }
      deny_message: "&cПодожди ещё {cooldown} сек."
```

## Плейсхолдеры

| плейсхолдер | что подставляет |
|---|---|
| `{player}` `{uuid}` | имя / UUID игрока |
| `{world}` `{x} {y} {z}` | текущий мир и координаты |
| `{health}` `{level}` | здоровье и уровень опыта |
| `{result}` | результат последнего `call` в этой же цепочке actions |

## GUI-меню

Меню строятся из секции `menus:` и открываются командой `/nano menu <аддон> <меню>`
или action-ом `openmenu` — вложенность произвольная: меню → подменю →
под-подменю и так далее.

**Видимость пункта по условию** — `if:` прямо на пункте (соседний ключ с
`material`/`name`/`actions`) скрывает кнопку целиком, если условие не
выполняется:

```yaml
items:
  "14":
    material: NETHER_STAR
    name: "&dСекретная кнопка"
    if: { permission: nano.vip }
    actions: [ { type: message, text: "&aТы VIP!" } ]
```

**Редактор в игре** — `/nano edit <аддон> <меню>`:

- обычное перетаскивание предмета в слот — задаёт иконку кнопки (материал,
  имя, лор, количество сохраняются в `addon.yml` автоматически);
- пустой слот после переноса — пункт удаляется целиком;
- **shift+клик** по кнопке — открывает ввод её логики через чат, простым
  DSL (`ActionLineParser`), заменяющим весь список `actions` этого пункта:

  ```
  message <текст>          broadcast <текст>        console <команда>
  call <плагин> <метод> [аргументы]                 openmenu <меню> [аддон]
  closemenu                setvar <ключ> <значение> [global]
  addvar <ключ> <число> [global]                     eco_give/eco_take <число>
  cancel                   - отменить, ничего не менять
  ```

  Для нескольких действий подряд по-прежнему проще отредактировать
  `addon.yml` вручную — чат-DSL рассчитан на быструю правку одного action.

## Переменные и кулдауны

У каждого аддона — свой `storage.yml` (переменные игрока или глобальные,
плюс кулдауны), создаётся автоматически при первом использовании
`setvar`/`addvar`/`cooldown`. Ничего настраивать заранее не нужно.

## Интеграции

Всё — через рефлексию, без compile-time зависимостей, поэтому плагин
собирается и работает даже если ничего из списка не установлено:

- **Любой плагин сервера** — `type: call` + `target-api.txt`.
- **Vault** (экономика) — `eco_give`/`eco_take`/`eco_at_least`. Использует
  стабильный интерфейс `net.milkbowl.vault.economy.Economy`.
- **WorldGuard 7.x** (регионы) — `if: region`. Другие версии API могут не
  сработать — в этом случае условие просто не проходит, с предупреждением
  в консоли, ничего не ломается.
- **PlugMan / PlugManX** — если целевой плагин аддона установлен, но
  выключен, `/nano enable` и `/nano info` показывают игроку кликабельную
  кнопку в чате, включающую его через `/plugman enable <плагин>`. NanoForge
  сам плагины не включает — это отдаётся PlugMan'у.

Если Vault/WorldGuard не установлены — при первой попытке их использовать
в консоль уходит одна понятная строка, а не тишина и не ошибка.

`softdepend: [Vault, WorldGuard]` в `plugin.yml` гарантирует правильный
порядок загрузки, если они есть на сервере.

## Надёжность и обработка ошибок

- Один синтаксически кривой `addon.yml` не мешает загрузке остальных
  аддонов и не роняет сервер — папка пропускается с предупреждением.
- Каждый action выполняется в собственном `try-catch` — ошибка в одном
  (опечатка в методе, недостающий плагин) не прерывает остальные и не
  сыплет стектрейсом, а пишет одну строку в консоль.
- То же самое на границах: команда аддона, обработчик события, клик по
  меню — нигде наружу не прорывается сырой Java stack trace.
- `/nano enable` проверяет, что целевой плагин аддона реально существует и
  включён, прежде чем регистрировать что-либо. На старте сервера проверка
  мягкая (без отказа) — порядок загрузки плагинов не гарантирован.
- Повторный `/nano enable` уже включённого аддона идемпотентен — старые
  регистрации (команды/события) корректно снимаются перед новыми, без
  задвоения.
- `/nano disable` снимает листенер со всех событий Bukkit разом
  (`HandlerList.unregisterAll`) — не просто флаг, а настоящее отключение.

## Структура пакетов

```
ru.nanodev.nanoforge
 ├── NanoForgePlugin.java  - точка входа
 ├── model/       - Addon: модель одного аддона (обёртка над addon.yml)
 ├── manager/     - AddonManager: загрузка/создание/enable-disable
 ├── storage/     - AddonStorage: переменные и кулдауны
 ├── engine/      - ActionRunner, ConditionChecker, PlaceholderUtil, ActionLineParser
 ├── dynamic/     - DynamicCommand/DynamicListener: регистрация в Bukkit "на лету"
 ├── integration/ - ReflectionBridge, VaultBridge, WorldGuardBridge, PlugManBridge
 ├── inspect/     - TargetInspector: дамп API целевого плагина
 ├── command/     - NanoCommand, ChatButtons
 └── gui/         - MenuManager, NanoMenuHolder
```

Что-то ЗНАЧИТ (`model`, `storage`) отдельно от того, что что-то ДЕЛАЕТ
(`engine`, `integration`), отдельно от того, что регистрируется в Bukkit
(`dynamic`, `command`, `gui`).

## Сборка

Нужен Maven и **JDK 17+** для самой сборки — не потому что плагин требует
Java 17 в рантайме, а потому что `spigot-api 1.20.4` сам скомпилирован под
Java 17 (class file version 61), и более старый `javac` физически не может
прочитать этот jar как зависимость ("bad class file ... should be 52.0").

При этом `maven.compiler.release=8` в `pom.xml` гарантирует, что
**собранный плагин** остаётся на уровне байткода Java 8 — грузится и на
старых 1.16-серверах, где сама Minecraft ещё не требует Java 17. Собирать
JDK 17, запускать на любом JDK 8+ — так и должно быть.

```bash
mvn clean package
```

Готовый джарник — `target/NanoForge.jar`.

## Известные ограничения

- Обычный vanilla shift-клик предметом ИЗ своего инвентаря В открытое
  меню (в режиме `/nano edit`) переносит предмет штатно, но это не
  отслеживается и не сохраняется в `addon.yml` — сохраняется только прямое
  перетаскивание на конкретный слот.
- Чат-DSL редактора меню поддерживает один action на пункт; для списка из
  нескольких actions нужно редактировать `addon.yml` вручную.
- `region:` нацелен на WorldGuard 7.x; другие версии API могут не
  распознаться (деградирует безопасно, без падений).
- `target-api.txt` дампит все классы jar'а целиком, включая шейдед-зависимости.

Полная история изменений — в [CHANGELOG.md](CHANGELOG.md). Лицензия — MIT
([LICENSE](LICENSE)).

## Автосборка и автовыпуск релизов (GitHub Actions)

- **`.github/workflows/ci.yml`** — на каждый push и pull request: собирает
  проект и прогоняет все тесты (`mvn clean verify`), прикладывает собранный
  джарник как build-артефакт (не релиз).
- **`.github/workflows/release.yml`** — на каждый push в `main`/`master`:
  читает версию НАПРЯМУЮ из `src/main/resources/plugin.yml` через GitHub
  Contents API (`api.github.com/repos/.../contents/...`), собирает проект,
  и если тега `vX.Y.Z` с такой версией ещё нет — публикует GitHub Release с
  джарником во вложении. Никаких дополнительных секретов заводить не нужно:
  используется встроенный `GITHUB_TOKEN`, который GitHub Actions
  предоставляет автоматически.

  Чтобы выпустить новый релиз — просто поднять `version:` в `plugin.yml`
  (и для порядка — версию в `pom.xml`) и запушить в `main`. Если версия не
  менялась — тег уже существует, и workflow просто ничего не публикует
  повторно.

## Проверка версии сервера и баннер при старте

При каждом включении плагина в консоль выводится баннер (версия, контакт
автора) и проверяется версия Minecraft на сервере: если она ниже 1.16 или
выше 1.21.11 — печатается предупреждение (плагин всё равно пытается
запуститься, так как Bukkit API обычно обратно совместим, но это не
гарантировано вне протестированного диапазона). Логика сравнения версий
вынесена в чистую функцию `StartupChecks.classify(String)` и покрыта
юнит-тестами на граничные случаи.

## Тесты

`pom.xml` подключает: JUnit 5 (Jupiter, включая параметризованные тесты),
Mockito (включая `mockStatic` для точечных подмен `Bukkit.*` без реального
сервера — работает из коробки с Mockito 5.x, без отдельного
`mockito-inline`), AssertJ.

Покрывают: парсер чат-DSL для правки меню (`ActionLineParserTest`),
подстановку плейсхолдеров (`PlaceholderUtilTest`), условия `if` включая
права/мир/переменные/кулдауны (`ConditionCheckerTest`), хранилище
переменных (`AddonStorageTest`), безопасное поведение интеграций при
отсутствии Vault/WorldGuard/PlugMan (`IntegrationBridgesTest`), границы
поддерживаемых версий сервера (`StartupChecksTest`).

```bash
mvn test          # только тесты
mvn clean verify  # тесты + сборка
```

### Почему без MockBukkit

Полноценная имитация целого Bukkit-сервера в памяти (MockBukkit) — штука
удобная, но требует точного совпадения версии с `spigot-api`. Две попытки
её подключить провалились по разным причинам: сначала не резолвился
транзитивный `paper-api` (не хватало репозитория PaperMC), потом
`MockBukkit-v1.20` оказался несовместим в рантайме именно с `spigot-api
1.20.4` — падал с `NullPointerException` при инициализации
`PotionEffectType` ещё до старта самих тестов. Без доступа в интернет
подобрать точно совместимую пару версий надёжно нельзя, поэтому вместо
эмуляции целого сервера тестируется изолированная логика через точечные
моки — это менее эффектно, но не зависит от версии стороннего мок-сервера
и не ломается от несовпадения патчей API.
